# Option A real-P dev failure analysis

This is **synthetic dev data only**. It does not use the frozen held-out suite, private bindings, or the abandoned final-v1 checkpoints. The original 2026-09-27 P study saved final outcomes and call costs, but did **not** save parsed NLU slots, intermediate responses, or matcher candidates. The tables therefore pair each **original failed outcome** with a new, budget-gated trace of the same dev scenario on the pre-fix code. The new trace is a reproduction, not a claim that an unrecorded original slot had the same value. One case changed outcome on rerun, as noted below. `txn_1`, etc. are opaque handles in the project-generated fixture, not organizer records.

The deterministic mock-NLU/B1 path was rerun on these exact 17 cases before any fix: all **9/9** original no-fault failures passed and all **8/8** fault fixtures reached their declared trigger and passed. Thus none of the 17 failures reproduced with mock NLU. The mock result does not prove the model is at fault: B1 bypasses the learned MATCH choice behavior and retains its older `no reconozco` dispute classifier.

In the tables, `CI` means `charge_inquiry`, `DC` means `dispute_charge`, `m` is merchant, `a` is amount/currency, `t` is the raw `type_expr`, and `∅` means absent. Expected NLU follows Sebastian's rule: **“no reconozco / não reconheço” without a denial or filing request is CI**. Candidate lists are ranked opaque handles. “Choice → retry → handoff” means the first response offered candidates, the scripted customer said “no sé / não sei” twice, and the conversation set `terminal_handoff_id`; the policy engine was never called. These are observed API responses plus the saved conversation fields; the app has no separate named state enum.

## Change and owner handoff

**AI lane:** Prompt v4 now tells the model not to put generic charge words into `type_expr`; deterministic postprocessing drops those words if a model still emits them. This preserves the customer's intent and merchant while preventing a generic word from masquerading as a literal ledger transaction type. The dev matcher regression verifies the specific pending-charge sensitivity. One post-fix real P check of `pt.pending.v2` passed with null normalized type, `propose [txn_2]`, policy explanation, and no unsafe outcome. This is one check, not the 20-case acceptance gate. No NLG cause was found; no NLG text changed.

**Lead / simulated customer and fixtures:** For explanation cases where MATCH safely offers choices, give the simulated customer a target choice when the target is present; keep a separate no-choice/handoff fixture. For the dispute and fault fixtures, either make the first utterance an explicit denial or filing request (and supply choice replies), or change the expected outcome to an inquiry. The latter would not exercise confirmation faults, so explicit denial/request is the useful fault-fixture correction. The newly authored 20-case confirmation set has fresh **explicit denials** for its four dispute/choice cases; its bytes were frozen before this analysis and have not been run or tuned.

**Data/ML matcher:** Review whether an exact named merchant should sometimes be proposed rather than offered as a three-item choice. The observed choice lists include the target in all cases, but target rank varies for Mercado Verde. Do not loosen MATCH thresholds merely to satisfy a customer simulator; the harness must handle a legitimate choice. No matcher artifact, thresholds, or shared interface changed in this PR.

The shared `dev-gate/option-a` Postgres scope was independently read back before paid diagnosis: $1.00 enabled, zero charged. The 17-case diagnosis and one post-fix case used **40 reserved/settled attempts, $0.02748308 known and charged, zero unknown-cost attempts**, read back from that same scope. Every real attempt, including parallel Jev risk calls, used `PostgresSpendGate(scope="dev-gate/option-a", run_id="option-a")`; `.env` was not changed. The prior handoff-11 study spend is outside this allowance. The confirmation set and full Step 3 gate remain unrun for the lead after owner fixes/merge. No final program or release was started.
